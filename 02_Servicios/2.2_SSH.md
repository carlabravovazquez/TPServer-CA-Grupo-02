# 2.2. Acceso remoto por SSH con clave pública para root

## Objetivo

Instalar el servidor SSH en la máquina virtual y permitir que el usuario `root` ingrese en forma remota usando la **clave pública y la clave privada** provistas por la cátedra (archivo `Material_Adicional_TPVMCA.tar.gz`, ubicado en el directorio de `root`).

## Conceptos previos

**SSH** (*Secure Shell*) es un protocolo que permite administrar un equipo remoto a través de una conexión cifrada y también copiar datos de forma segura. Funciona con un **servidor** (`sshd`, en la VM) y un **cliente** (`ssh`, en la computadora física). El servidor escucha en el **puerto 22** (Universidad de Palermo, s. f., *SSH*, pp. 1–2).

**Autenticación con clave pública:** se usa un par de claves relacionadas (cifrado asimétrico). La **clave pública** se deja en el servidor, en el archivo `authorized_keys` del usuario; la **clave privada** la conserva el cliente y nunca se envía. Al conectarse, el servidor plantea un desafío que solo puede resolver quien tiene la clave privada correspondiente; si lo resuelve, entra **sin contraseña** (Universidad de Palermo, s. f., *SSH*, pp. 3–4; Niklas, 2020, pp. 202–207).

Archivos involucrados (Universidad de Palermo, s. f., *SSH*, pp. 1–2):

- `/etc/ssh/sshd_config`: configuración del **servidor** (la que se modifica);
- `/etc/ssh/ssh_config`: configuración del cliente (no se modifica);
- `/root/.ssh/authorized_keys`: claves públicas autorizadas para entrar como `root`.

### Parte B: autorizar la clave pública y configurar el servidor

```bash
ls -la /root/.ssh
cat /root/Material_Adicional_TPVMCA/clave_publica.pub
```

La carpeta `.ssh` está vacía. La clave pública es una sola línea que empieza con `ssh-rsa AAAAB3…` y termina con `sonda@ttys9-HP-ENVY-Notebook` (un comentario que identifica dónde se generó).

```bash
cat /root/Material_Adicional_TPVMCA/clave_publica.pub >> /root/.ssh/authorized_keys
```

`cat` muestra el archivo y **`>>`** envía esa salida al final de `authorized_keys`; si el archivo no existe, lo crea (Universidad de Palermo, s. f., *Redireccionamiento y Pipes*, p. 1). Se usa `>>` y no `>` para no borrar claves que ya estuvieran autorizadas.

**Figura 9.** Clave pública y primer intento (con error de tipeo, ver *Problemas*).

![authorized_keys error](Capturas/Captura%2002.37.png)

Después de corregir el comando:

```bash
cat /root/.ssh/authorized_keys
chmod 700 /root/.ssh
chmod 600 /root/.ssh/authorized_keys
ls -la /root/.ssh
cp /etc/ssh/sshd_config /etc/ssh/sshd_config.orig
```

**Permisos en formato octal** (Universidad de Palermo, s. f., *Permisos – Formato octal*, pp. 3–4): cada dígito corresponde a dueño, grupo y otros; lectura = 4, escritura = 2, ejecución = 1.

| Comando | Dueño | Grupo | Otros | Resultado en `ls` |
|---|---|---|---|---|
| `chmod 700 /root/.ssh` | 7 = rwx | 0 | 0 | `drwx------` |
| `chmod 600 …/authorized_keys` | 6 = rw- | 0 | 0 | `-rw-------` |

SSH rechaza las claves si otros usuarios pueden leer o modificar estos archivos, por eso solo el dueño (`root`) tiene permisos. Para escribir `chmod` se usó **Tab Tab** (`chm` + Tab Tab mostró `chmem chmod`).

**Figura 10.** Clave autorizada, permisos aplicados y respaldo de `sshd_config`.

![chmod](Capturas/Captura%2002.38.png)

```bash
vi /etc/ssh/sshd_config
```

Se modificaron tres directivas (Universidad de Palermo, s. f., *SSH*, p. 2; actividad *SSH*, p. 1). Una línea que empieza con `#` es un comentario y no tiene efecto; para activarla se borra el `#`.

| Línea | Antes | Después | Para qué |
|---|---|---|---|
| 33 | `#PermitRootLogin prohibit-password` | `PermitRootLogin yes` | Permite el ingreso de `root` |
| 38 | `#PubkeyAuthentication yes` | `PubkeyAuthentication yes` | Activa la autenticación por clave pública |
| 41 | `#AuthorizedKeysFile .ssh/authorized_keys .ssh/authorized_keys2` | `AuthorizedKeysFile .ssh/authorized_keys .ssh/authorized_keys2` | Indica dónde buscar las claves autorizadas |

Teclas en `vi` (*Editores de texto*, pp. 2–4):

- **PermitRootLogin:** `/PermitRootLogin` + Enter (busca la línea) → **←** → `x` (borra el `#`) → **→** hasta la `p` de `prohibit-password` → `i` → `yes` → **Esc** → **→** → `x` ×17 (borra `prohibit-password`).
- **PubkeyAuthentication:** `/PubkeyAuthentication` + Enter → **←** → `x`.
- **AuthorizedKeysFile:** `/AuthorizedKeysFile` + Enter → **←** → `x`.
- **Guardar y salir:** **Esc** → `:wq` + Enter. (Para salir sin guardar si algo sale mal: **Esc** → `:q!` + Enter.)

**Figura 11.** Las tres directivas modificadas.

![sshd_config](Capturas/Captura%2002.39.png)

Verificación con `grep`, que muestra solo las líneas que contienen un texto (Universidad de Palermo, s. f., *Streams y filtros*, p. 3):

```bash
grep PermitRootLogin /etc/ssh/sshd_config
grep PubkeyAuthentication /etc/ssh/sshd_config
grep AuthorizedKeysFile /etc/ssh/sshd_config
```

`vi` había confirmado `"/etc/ssh/sshd_config" 122L, 3206B escritos`. Las tres líneas aparecen sin `#`. (Al completar la ruta con Tab Tab en `/etc/ssh/` se ve también el respaldo `sshd_config.orig`.)

`restart` reinicia el servicio para que lea la configuración nueva (actividad *SSH*, p. 1; *Init y Systemd*, p. 4). El estado muestra `active (running)` y la línea **`ExecStartPre=/usr/sbin/sshd -t … status=0/SUCCESS`**: antes de arrancar, SSH comprueba la sintaxis del archivo (`-t` = *test*); si hubiera un error de escritura, el servicio no arrancaría. `ip a` confirma la dirección de la VM: `192.168.0.209`.

**Figura 14.** Servicio reiniciado sin errores y dirección IP de la VM.

**Por qué `PermitRootLogin yes`:** es el valor que indica el apunte *SSH* (p. 2). Dato para la defensa: con `yes`, `root` también podría entrar con contraseña; si se quisiera permitir **solo** la clave, el valor sería `prohibit-password` (el valor por defecto de Debian, según `man sshd_config`).

## Problemas encontrados y solución

Al autorizar la clave pública, el primer intento falló con el mensaje *No existe el fichero o el directorio*, por un error de tipeo en la ruta (`Material_Adcional` en lugar de `Material_Adicional`). Como el `>>` se procesa antes de ejecutar el comando, igualmente se creó un archivo `authorized_keys` vacío. Se repitió el comando con la ruta correcta, esta vez completándola con **Tab** para evitar nuevos errores, y se comprobó con `cat` que la clave hubiera quedado guardada.

Durante la verificación, un `grep` no devolvió resultados porque se había escrito `Authetication` en lugar de `Authentication`. Se limpió la pantalla con **Ctrl + L** y se repitió la búsqueda con el nombre correcto.

Por último, al revisar el `history` se observó que no figuraban los comandos escritos en la consola durante este punto (`tar`, `apt-get`, `chmod`, `vi`, etc.): la lista pasaba de `47 shutdown -h now`, del punto anterior, a `48 exit`. Bash guarda el historial en disco recién cuando la sesión se cierra en forma ordenada. En este caso, la máquina se apagó cerrando la ventana de VirtualBox con la opción "Apagar la máquina", y el historial que estaba en memoria se perdió. El `exit` de la línea 48 corresponde a la sesión SSH desde Windows, que sí se cerró correctamente. Todos los comandos del punto quedaron registrados en las capturas, y a partir de entonces la máquina se apagó siempre con `shutdown -h now`.

## Resultado

El servidor OpenSSH quedó instalado y activo. `root` ingresa desde la computadora física con la clave privada de la cátedra y **sin contraseña**, lo que confirma el registro `Accepted publickey for root` en `/var/log/auth.log`.

**Instantánea de VirtualBox:** `04 - Punto 2.2 SSH`.
